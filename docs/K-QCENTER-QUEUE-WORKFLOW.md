# กระบวนการจอง เช็กอิน และให้บริการคิว K-QCENTER

เอกสารนี้เป็นข้อกำหนดกระบวนการทำงานร่วมกันของ K-QOnline, Kiosk, K-QCENTER, K-QCounter, K-QDisplay และ HOSxP ใช้ประกอบกับ `K-QCENTER-SYSTEM-SPEC.md` โดย K-QCENTER เป็นแหล่งข้อมูลหลักของ Slot, Capacity, Booking และสถานะคิว

## 1. เป้าหมาย

1. รองรับการรับคิว 2 ช่องทาง ได้แก่ จองออนไลน์และ Walk-in
2. ให้ผู้จองออนไลน์ยืนยันว่ามาถึงสถานที่จริงก่อนเข้าลำดับรอ
3. รวมคิวจากทุกช่องทางไว้ในระบบกลางโดยไม่เกิน Capacity ของแผนก
4. ให้ผู้รับบริการติดตามสถานะและเวลาที่ควรมารอได้โดยไม่ต้องนั่งรอหน้างานนาน
5. ให้เวชระเบียนเรียกตามลำดับ เปิด Visit ใน HOSxP และติดตามเวลาให้บริการรวมไม่เกิน 120 นาทีต่อ Visit

## 2. องค์ประกอบระบบ

```text
K-QOnline ──จอง Slot──┐
                      ├── K-QCENTER API ── Queue Engine ── K-QCounter
Kiosk ──Walk-in───────┤          │                  ├────── K-QDisplay
      └─Check-in──────┘          │                  └────── Monitor มือถือ
                                 └── HOSxP Integration Adapter
```

- **K-QOnline**: ค้นหา Slot จอง รับ QR/รหัสยืนยัน และติดตามคิว
- **Kiosk**: สแกน QR จากมือถือ อ่านบัตร ระบุรหัสยืนยัน และออกบัตรคิว Walk-in
- **Kiosk Status**: สแกน QR ที่ K-QCENTER ออกให้เพื่อดูสถานะปัจจุบัน ลำดับขั้น และเวลารอโดยประมาณ
- **K-QCENTER**: ตรวจสิทธิ์ คุม Capacity ออกเลขคิว และเก็บสถานะส่วนกลาง
- **K-QCounter**: หน้าจอเจ้าหน้าที่เวชระเบียนสำหรับเรียก เริ่ม พัก ส่งต่อ และจบคิว
- **K-QDisplay**: จอประกาศหมายเลขคิวและช่องบริการ โดยไม่แสดงข้อมูลส่วนบุคคล
- **HOSxP Adapter**: ชั้นเชื่อมต่อสำหรับค้น/ยืนยันผู้ป่วยและเปิด Visit ห้าม Client หรือ Kiosk เชื่อมฐานข้อมูล HOSxP โดยตรง

## 3. ช่องทางที่ 1: จองออนไลน์ผ่าน K-QOnline

### 3.1 การจอง

1. ผู้ใช้เลือกสาขา แผนก ประเภทบริการ วันที่ และ Slot
2. K-QCENTER แสดงเฉพาะ Slot ที่แผนกเปิดและยังมีโควตา Online
3. เมื่อเลือก Slot ระบบ Hold Capacity ชั่วคราว 3–5 นาที
4. ผู้ใช้ยืนยันการจอง ระบบสร้าง Booking และคืน QR Code พร้อมรหัสยืนยันตัวเลข
5. สถานะเป็น `CONFIRMED` แต่ยังไม่เข้าสู่ลำดับเรียกหน้างาน
6. แอปแจ้งเตือนก่อนเวลานัดและบอกช่วงเวลาเช็กอิน

### 3.2 การยืนยันที่ Kiosk

ผู้ใช้ยืนยันได้อย่างน้อย 2 วิธี:

- สแกน QR Code จากหน้าจอมือถือ
- กรอกรหัสยืนยันด้วยแป้นตัวเลขบน Kiosk

อาจใช้การอ่านบัตรเพื่อยืนยันตัวบุคคลเพิ่มเติมตามนโยบายของหน่วยงาน แต่ต้องขอความยินยอมและไม่เก็บข้อมูลจากบัตรเกินความจำเป็น

ลำดับการทำงาน:

1. Kiosk ส่ง Token หรือรหัสยืนยันไปยัง Check-in API ผ่าน HTTPS
2. K-QCENTER ตรวจ Booking, สาขา, แผนก, วันที่, ช่วงเวลา และสถานะ
3. หากถูกต้อง ระบบใช้ Token ครั้งเดียว เปลี่ยนเป็น `CHECKED_IN` และสร้าง Queue Ticket
4. ระบบพิมพ์หรือแสดงหมายเลขคิว พร้อมเวลารอโดยประมาณ
5. เมื่อพร้อมเข้าสู่ลำดับเรียก สถานะเปลี่ยนเป็น `WAITING`

Booking ที่ไม่เช็กอินภายในเวลาที่กำหนดต้องไม่เข้าคิวอัตโนมัติ ระบบอาจให้ Grace period เช่น ก่อน Slot 30 นาทีถึงหลัง Slot 15 นาที และให้เจ้าหน้าที่อนุมัติกรณีพิเศษได้

## 4. ช่องทางที่ 2: Walk-in ผ่าน Kiosk

หน้า Kiosk ต้องรองรับ:

- อ่านบัตรตามอุปกรณ์และสิทธิ์ที่องค์กรกำหนด
- สแกน QR Code
- กรอกหมายเลขหรือรหัสด้วยแป้นตัวเลขบนหน้าจอ
- เลือกเมนู `ตรวจสอบสถานะคิว` แล้วสแกน QR ที่ K-QCENTER ออกให้
- เลือกภาษาและใช้ปุ่มขนาดใหญ่ที่เข้าถึงได้
- เลือกแผนกหรือบริการที่เปิดรับ Walk-in ในขณะนั้น

ลำดับการทำงาน:

1. ผู้ใช้ระบุตัวตนหรือเลือกดำเนินการตามนโยบายของบริการ
2. Kiosk ขอรายการแผนก/บริการที่เปิดจาก K-QCENTER API
3. K-QCENTER ตรวจเวลาทำการ Daily Override จำนวนช่องที่เปิด คิวสะสม เวลาปิด และโควตา Walk-in
4. ระบบแสดงเฉพาะบริการที่ยังรับคิวได้ พร้อมเวลารอโดยประมาณ
5. เมื่อยืนยัน ระบบจอง Capacity และสร้าง Queue Ticket ใน Transaction เดียวกัน
6. สถานะเริ่มต้นเป็น `WAITING` และพิมพ์หรือแสดงบัตรคิว

ถ้าโควตา Walk-in เต็ม ระบบต้องไม่ออกเลขคิวลอย แต่เสนอ Slot ถัดไป การจองวันอื่น หรือส่งให้เจ้าหน้าที่พิจารณาโควตาสำรอง

### 4.1 ตรวจสอบสถานะด้วย QR ที่ Kiosk

QR ที่ K-QCENTER ออกหลังการจองหรือออกบัตรคิวต้องใช้ตรวจสอบสถานะที่ Kiosk ได้ โดยมีขั้นตอนดังนี้:

1. ผู้รับบริการเลือก `ตรวจสอบสถานะคิว` บนหน้าแรกของ Kiosk
2. สแกน QR จาก K-QOnline หรือบัตรคิวที่พิมพ์จาก Kiosk
3. Kiosk ส่ง Status Token ไปยัง K-QCENTER API ผ่าน HTTPS
4. ระบบตรวจ Token, วันหมดอายุ, องค์กร และสิทธิ์การเปิดเผยข้อมูล
5. แสดง Timeline ของคิว ขั้นตอนปัจจุบัน จุดที่ต้องไปต่อ เวลารอโดยประมาณ และคำแนะนำ
6. ผู้ใช้กด `เสร็จสิ้น` หรือระบบปิดหน้าจอและล้างข้อมูลอัตโนมัติเมื่อไม่มีการใช้งาน

การสแกนในเมนูนี้เป็นแบบอ่านอย่างเดียว ต้องไม่เปลี่ยนสถานะ ไม่สร้างคิวใหม่ และไม่ถือเป็นการ Check-in หากผู้ใช้ยังไม่ได้ยืนยันการมาถึง ระบบต้องแสดงปุ่มแยกต่างหากและขอให้ผู้ใช้ยืนยันก่อนทำ Check-in

## 5. Slot และการรวม Capacity

แต่ละแผนกกำหนด Slot จาก:

- ตารางเปิดของอาคาร สาขา และแผนกที่ซ้อนทับกัน
- Daily Override หรือการปิดบริการเฉพาะวัน
- จำนวนช่องบริการจริง
- เวลาเฉลี่ยของประเภทบริการ
- Efficiency
- Online, Walk-in และ Reserve quota
- Closing buffer และงานค้างปัจจุบัน

Online และ Walk-in ใช้ Capacity Pool เดียวกันแต่แบ่งโควตาตามค่าที่ตั้งไว้ ระบบอาจคืนโควตา Online ที่ยังว่างให้ Walk-in ก่อนเริ่ม Slot ตามกฎของแผนก การสร้าง Booking และ Queue Ticket ต้องเป็น Transaction, ป้องกันยอดติดลบ และรองรับ `Idempotency-Key`

## 6. ลำดับคิวและ Priority

ลำดับพื้นฐานให้พิจารณาจาก:

1. Priority ทางบริการหรือทางการแพทย์ที่ได้รับอนุญาต
2. Slot ที่นัดหมาย
3. เวลา Check-in
4. ลำดับการออก Queue Ticket

การจองออนไลน์ไม่ได้ให้สิทธิ์แซงทุกคิว และ Walk-in ไม่ควรเบียด Slot ที่จองไว้ ระบบต้องแสดงเหตุผลทุกครั้งที่เจ้าหน้าที่ข้าม ย้าย หรือปรับ Priority พร้อมเก็บ Audit log

## 7. สถานะคิว

```text
Online: HELD → CONFIRMED → CHECKED_IN → WAITING
Walk-in:                         CREATED → WAITING
                                     WAITING → CALLED → REGISTRATION → VISIT_OPEN
                                                           │              │
                                                           └→ NO_SHOW     └→ SERVING → COMPLETED
```

สถานะเพิ่มเติมที่ต้องรองรับ ได้แก่ `CANCELLED`, `EXPIRED`, `SKIPPED`, `PAUSED` และ `TRANSFERRED` โดยทุกการเปลี่ยนสถานะต้องมีเวลา ผู้ดำเนินการ จุดบริการ และเหตุผลตามความเหมาะสม

## 8. Monitor สำหรับผู้รับบริการ

หลังได้รับ Queue Ticket ผู้รับบริการติดตามได้จาก K-QOnline หรือหน้าเว็บสถานะด้วย Token ที่คาดเดายาก โดยแสดง:

- หมายเลขคิวของตน
- สถานะปัจจุบัน
- จำนวนคิวโดยประมาณก่อนถึงคิว
- เวลารอและช่วงเวลาที่แนะนำให้มารอใกล้จุดบริการ
- การเรียกคิว เรียกซ้ำ เปลี่ยนช่อง หรือมีความล่าช้า
- คำแนะนำเมื่อมาสายหรือพลาดการเรียก

ข้อมูลชุดเดียวกันต้องเปิดดูได้ที่ Kiosk ด้วยการสแกน QR โดยแสดงเป็น Timeline ที่เข้าใจง่าย เช่น:

```text
✓ ยืนยันการจอง
✓ เช็กอินแล้ว
✓ เวชระเบียนเรียกและเปิด Visit แล้ว
● กำลังรอตรวจที่แผนก
○ รอรับบริการขั้นตอนถัดไป
○ เสร็จสิ้น
```

แต่ละขั้นแสดงเวลาในปฏิทิน พ.ศ. และเขตเวลา Asia/Bangkok พร้อมเวลารอโดยประมาณ หากระบบยังคำนวณไม่ได้ให้แสดง `กำลังประเมินเวลา` แทนการแสดงค่าที่อาจทำให้เข้าใจผิด

การประมาณเวลาต้องปรับจากความเร็วให้บริการจริงและจำนวนช่องที่เปิด ไม่ควรรับประกันเป็นเวลาตายตัว จอสาธารณะแสดงเฉพาะหมายเลขคิวและช่อง ห้ามแสดงชื่อ HN เลขบัตร หรือข้อมูลสุขภาพ

## 9. เวชระเบียนและ HOSxP

1. K-QCounter เรียก Queue Ticket ตามกฎลำดับคิว
2. เมื่อเจ้าหน้าที่รับผู้ใช้ ให้บันทึก `registration_started_at`
3. HOSxP Adapter ตรวจสอบผู้ป่วยและร้องขอเปิด Visit
4. เมื่อ HOSxP ตอบกลับ ให้เก็บเฉพาะตัวอ้างอิงที่จำเป็น เช่น Visit reference และ `visit_opened_at`
5. เมื่อส่งต่อจุดบริการ ให้ K-QCENTER บันทึกสถานะและเวลาแต่ละช่วง
6. เมื่อจบบริการ ให้บันทึก `service_completed_at` และสถานะ `COMPLETED`

ห้าม Kiosk, K-QOnline หรือหน้า Counter เชื่อมฐานข้อมูล HOSxP โดยตรง การเชื่อมต่อควรผ่าน Adapter/API ที่มีบัญชีบริการสิทธิ์ต่ำสุด การเข้ารหัส Timeout, Retry, Idempotency และ Audit log

หาก HOSxP ไม่พร้อมใช้งาน ให้คิวยังคงอยู่ใน K-QCENTER และเข้าสู่รายการรอดำเนินการ ห้ามเปิด Visit ซ้ำเมื่อเชื่อมต่อกลับมา

## 10. กรอบเวลาไม่เกิน 120 นาทีต่อ Visit

กำหนด SLA หลักดังนี้:

```text
visit_elapsed = service_completed_at - registration_started_at
เป้าหมาย: visit_elapsed <= 120 นาที
```

เก็บเวลาแยกเพื่อวิเคราะห์คอขวด:

- `checked_in_at`: ยืนยันมาถึงสถานที่
- `first_called_at`: ถูกเรียกครั้งแรก
- `registration_started_at`: เริ่มเวชระเบียนและเริ่มนับ SLA Visit
- `visit_opened_at`: HOSxP เปิด Visit สำเร็จ
- `service_started_at`: เริ่มรับบริการหลัก
- `service_completed_at`: จบบริการทั้งหมดและหยุดนับ SLA

ระดับแจ้งเตือนเริ่มต้น:

| เวลาที่ใช้ | ระดับ | การดำเนินการ |
|---:|---|---|
| 0–89 นาที | ปกติ | ติดตามตามปกติ |
| 90–104 นาที | เฝ้าระวัง | แสดงสีเหลืองแก่เจ้าหน้าที่ |
| 105–119 นาที | เสี่ยงเกิน SLA | แสดงสีแดงและแจ้งหัวหน้าแผนก |
| ตั้งแต่ 120 นาที | เกิน SLA | Escalate และบังคับระบุสาเหตุเมื่อปิด Visit |

K-QCENTER ต้องไม่เปลี่ยนข้อมูลเวลาของ HOSxP แต่เก็บเวลาเหตุการณ์ของตนเองเป็น UTC/ISO 8601 และแสดงเป็น พ.ศ. เวลา Asia/Bangkok รายงานต้องแยกเวลารอก่อนเวชระเบียนออกจากเวลา Visit เพื่อให้วิเคราะห์ได้ถูกต้อง

## 11. ความปลอดภัยของ QR และ Kiosk

- QR มีเพียง Token แบบสุ่มหรือข้อมูลที่ลงลายมือชื่อ ห้ามมี HN เลขบัตร ชื่อ หรือข้อมูลสุขภาพแบบอ่านได้
- แยกวัตถุประสงค์ Token ให้ชัดเจน: Check-in Token ใช้ครั้งเดียว ส่วน Status Token ใช้ดูข้อมูลแบบอ่านอย่างเดียวและเพิกถอนได้
- Token ต้องมีวันหมดอายุและผูกกับ Booking/Queue Ticket/องค์กรที่เหมาะสม
- รหัสตัวเลขต้องมีอายุ จำกัดจำนวนครั้งที่ลอง และ Rate limit ต่อ Kiosk/IP/Booking
- Kiosk ใช้ Device identity หรือ Client certificate และมีสิทธิ์เฉพาะ Check-in/Walk-in
- ใช้โหมด Kiosk ล็อกไม่ให้เข้าระบบปฏิบัติการหรือ Admin
- ล้างข้อมูลบนหน้าจอและ Session หลังจบรายการหรือไม่มีการใช้งาน
- หน้า Status ต้องไม่แสดงชื่อเต็ม HN เลขบัตร การวินิจฉัย หรือรายละเอียดการตรวจบนจอสาธารณะ หากต้องยืนยันเจ้าของคิวให้แสดงข้อมูลแบบปิดบัง
- Admin, Database, Redis และ HOSxP ห้ามเปิดผ่าน Tailscale Funnel

## 12. ข้อมูลและเหตุการณ์สำคัญ

Entity ที่ต้องมีเพิ่มเติมหรือกำหนดให้ชัดเจน:

- `KioskDevice`: จุดติดตั้ง สาขา Device identity และสถานะ
- `BookingCheckInToken`: Hash ของ Token วันหมดอายุ เวลาใช้ และช่องทาง
- `QueueTicket`: ช่องทาง `ONLINE`/`WALK_IN` หมายเลขคิว Slot และ Priority
- `QueueEvent`: สถานะเดิม/ใหม่ เวลา ผู้ดำเนินการและเหตุผล
- `ServiceSession`: เวลาเวชระเบียน เวลาเปิด Visit เวลาเริ่ม/จบ และ SLA
- `ExternalVisitReference`: ตัวอ้างอิง HOSxP โดยไม่เก็บข้อมูลเกินจำเป็น

เลขคิวที่แสดงต่อผู้ใช้สามารถวนใหม่รายวันได้ แต่ Primary key และ Public identifier ต้องไม่ซ้ำและคาดเดายาก

## 14. กรณีผิดปกติที่ต้องทดสอบ

- สแกน QR ซ้ำหรือกรอกรหัสผิดหลายครั้ง
- สแกน Status QR ที่หมดอายุ ถูกเพิกถอน หรือเป็นขององค์กรอื่น
- สแกนเพื่อดูสถานะแล้วต้องไม่ Check-in หรือเปลี่ยนสถานะคิวโดยไม่ได้ยืนยัน
- เช็กอินผิดสาขา เร็วหรือช้ากว่าช่วงที่กำหนด
- Online และ Walk-in ขอ Capacity สุดท้ายพร้อมกัน
- Kiosk พิมพ์บัตรไม่ออกหลังสร้างคิวสำเร็จ
- Network ขาดระหว่าง Check-in โดยต้องไม่สร้างคิวซ้ำ
- HOSxP ตอบช้า ปิดระบบ หรือเปิด Visit สำเร็จแต่ตอบกลับไม่ถึง K-QCENTER
- ผู้ใช้ไม่มาเมื่อเรียก มาสาย ย้ายแผนก หรือถูกส่งต่อ
- ช่องบริการลดลงและคิวมีความเสี่ยงเกิน 120 นาที
- ระบบข้ามวันหรือแผนกที่เปิด 24 ชั่วโมง

## 15. ตัวชี้วัด

- จำนวน Online booking, Online check-in และ Walk-in
- อัตรา Online no-show และ Check-in สำเร็จ
- เวลาจาก Check-in ถึงถูกเรียกครั้งแรก
- เวลาลงทะเบียนและเวลาเปิด Visit ใน HOSxP
- ระยะเวลา Visit รวม และสัดส่วนที่เสร็จภายใน 120 นาที
- เวลารอเฉลี่ยแยกตามสาขา แผนก Slot และช่องทาง
- Capacity utilization และจำนวนครั้งที่ปฏิเสธเพราะเต็ม
- ความแม่นยำของเวลารอที่ประมาณไว้

## 16. ประเด็นที่ต้องยืนยันก่อนเชื่อม HOSxP จริง

1. วิธีเชื่อมต่อที่โรงพยาบาลอนุญาต เช่น API, Integration Engine หรือ Service ที่จัดทำขึ้นเฉพาะ
2. Identifier ที่ใช้ค้นผู้ป่วยและข้อมูลขั้นต่ำที่ K-QCENTER มีสิทธิ์เข้าถึง
3. จุดเริ่มและจุดจบ SLA 120 นาทีที่องค์กรรับรองอย่างเป็นทางการ
4. ขั้นตอนเมื่อไม่พบผู้ป่วยหรือข้อมูลบัตรไม่ตรง
5. กฎ Priority ทางการแพทย์ ผู้มีสิทธิพิเศษ และผู้ป่วยฉุกเฉิน
6. ช่วง Check-in ก่อน/หลัง Slot และนโยบายผู้มาสาย
7. รูปแบบหมายเลขคิวและการแยกลำดับของแต่ละแผนก
