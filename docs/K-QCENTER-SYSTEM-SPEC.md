## 1. วัตถุประสงค์

K-QCENTER เป็นแพลตฟอร์มบริหารคิวส่วนกลาง ทำหน้าที่กำหนดสาขา แผนก บริการ เวลาทำการ กำลังให้บริการ Slot และสถานะคิวทั้งหมด ส่วน K-QOnline เป็น Mobile App ภายใต้ K-QCENTER สำหรับให้ประชาชนจองและติดตามคิวออนไลน์ในรูปแบบใกล้เคียงการจองตั๋วภาพยนตร์

การประกาศเรียกคิวของ K-QCounter อ่านหมายเลขคิว ชื่อผู้รับบริการโดยตัดคำนำหน้าชื่อออก และจุดติดต่อ โดยส่งชื่อเต็มเฉพาะผู้ใช้บทบาท `admin` หรือ `counter` ที่ผ่านการตรวจสอบขอบเขตสิทธิ์แล้ว หน้าสาธารณะและบทบาท `viewer` ยังคงเห็นเฉพาะชื่อที่ปกปิดบางส่วน
หากไม่มีชื่อ หรือเป็นคิวจากผู้รับบริการที่ไม่ใช้บัตรประชาชนและไม่ได้ระบุชื่อ ระบบใช้คำกลางว่า “ผู้รับบริการ” แทนชื่อในการแสดงผลและประกาศเสียง

แม่แบบประกาศรองรับตัวแปร `{queue}`, `{name}`, `{destination}` และตัวเลือกจังหวะ `{pause-short}`, `{pause-medium}`, `{pause-long}` โดยมีคำอธิบายและตัวอย่างแสดงใต้ช่องข้อความประกาศ

เสียงประกาศภายในเครื่องหรือจุดเดียวกันต้องเข้าคิวแบบ FIFO โดยรอให้ข้อความก่อนหน้าอ่านจบจึงเริ่มข้อความถัดไป เพื่อป้องกันเสียงซ้อนกัน ส่วนจุดบริการคนละจุดที่ใช้ลำโพงแยกสามารถประกาศพร้อมกันได้
หน้าตั้งค่าเสียงมีตัวเลือก “รออ่านจบทีละคิว” และ “อนุญาตให้อ่านพร้อมกัน” โดยค่าเริ่มต้นเป็นการรออ่านจบ และใช้กับการเรียกคิว เรียกซ้ำ และทดสอบเสียงทั้งหมดในอุปกรณ์นั้น
มีตัวเลือกป้องกันการกดคิวเดิมซ้ำระหว่างรายการนั้นกำลังรอหรือกำลังประกาศ ค่าเริ่มต้นต้องห้ามกดซ้ำจนกว่าเสียงของคิวเดิมอ่านจบ

เมนู “ตั้งค่าระบบ” เป็นศูนย์รวมการตั้งค่าระดับระบบสำหรับผู้ดูแล ประกอบด้วยการตั้งค่าเสียงเรียกคิว สถานะการเชื่อมต่อ API/MariaDB/HOSxP/HTTPS ทางลัดไปยัง Kiosk ปฏิทินและวันหยุด ผู้ใช้และสิทธิ์ และประวัติการใช้งาน ส่วนหน้า Monitor ห้องบัตรคงไว้เฉพาะปุ่มเปิดหรือปิดเสียงที่จำเป็นระหว่างปฏิบัติงาน

เป้าหมายหลักคือ:

1. ลดความแออัดในพื้นที่รอรับบริการ
2. ไม่เปิดรับคิวเกินกำลังของเจ้าหน้าที่
3. ทำให้คิวสุดท้ายเสร็จทันเวลาปิดทำการ
4. รองรับคิวออนไลน์ Walk-in คิวสำรอง และคิวพิเศษ
5. ให้สถานะคิวตรงกันระหว่าง Mobile App เคาน์เตอร์ และจอแสดงผล
6. มีความปลอดภัยและตรวจสอบย้อนหลังได้

## 2. ภาพรวมองค์ประกอบ

```text
K-QCENTER
├── K-QOnline          Mobile App สำหรับประชาชน
├── K-QAdmin           Web หลังบ้านสำหรับผู้ดูแล
├── K-QCounter         หน้าจอเจ้าหน้าที่เรียกและให้บริการคิว
├── K-QDisplay         จอแสดงหมายเลขคิว
├── K-QServer/API      กฎธุรกิจและ API ส่วนกลาง
├── K-QScheduler       สร้าง Slot และคำนวณ Capacity
├── K-QNotifier        Push / LINE / SMS
└── Database / Redis   ข้อมูลถาวรและการล็อกการจอง
```

K-QOnline, K-QAdmin, K-QCounter และ K-QDisplay ต้องสื่อสารผ่าน K-QCENTER API เท่านั้น ห้ามเชื่อมฐานข้อมูลโดยตรง

ระบบเรียกคิวภาษาไทยรองรับข้อความประกาศที่กำหนดเอง ตัวแปรเลขคิวและจุดติดต่อ พจนานุกรมคำอ่าน เลือกเสียงชาย/หญิง ความเร็ว และจำนวนครั้งที่อ่าน การเลือกเสียงจริงเก็บแยกต่อเครื่อง Monitor เพราะขึ้นอยู่กับเสียงภาษาไทยที่ติดตั้งในระบบปฏิบัติการและเบราว์เซอร์

เสียงหลักในระบบทดลองใช้ Piper `th_TH-tsync2-medium` บน K-QServer แบบ Offline และ cache ไฟล์ WAV ตามข้อความ/ความเร็ว โดย endpoint สร้างเสียงต้องผ่าน session และ CSRF ของผู้ใช้หลังบ้าน หากบริการ Offline ไม่พร้อม Client จะ fallback ไปยัง Web Speech ของเครื่อง Monitor อัตโนมัติ

## 3. สถาปัตยกรรมช่วงทดลอง

```text
ประชาชน / K-QOnline
        │ Public HTTPS
        ▼
 Tailscale Funnel
        │
        ▼
 Public API ที่ 10.9.1.22

เจ้าหน้าที่ / K-QAdmin / K-QCounter
        │ Private HTTPS + Tailnet identity
        ▼
  Tailscale Serve
        │
        ▼
 Internal services ที่ 10.9.1.22
```

ข้อกำหนด:

- ห้ามทำ Router Port Forward เข้าหา `10.9.1.22`
- Public API เปิดผ่าน Funnel เฉพาะ endpoint ที่ Mobile App จำเป็นต้องใช้
- K-QAdmin และ K-QCounter เปิดผ่าน Serve และเข้าถึงได้เฉพาะผู้ได้รับอนุญาตใน Tailnet
- ห้ามเปิด Database, Redis, phpMyAdmin, SSH หรือ RDP ผ่าน Funnel
- Application service ควร bind กับ `127.0.0.1` เมื่ออยู่บนเครื่องเดียวกับ Tailscale
- Firewall ใช้หลัก deny-by-default
- แยกข้อมูลและ credential ของระบบทดลองออกจาก Production

เมื่อขึ้น Production ให้ย้าย Public API ไปหลัง CDN/WAF/API Gateway บน Cloud หรือ DMZ และให้ `10.9.1.22` อยู่ในเครือข่ายภายใน เชื่อมต่อด้วย VPN หรือ outbound private tunnel

## 4. มาตรฐานหน้าจอและภาษา

### 4.1 ฟอนต์ Sarabun

ทุกส่วนต้องใช้ Sarabun ได้แก่:

- Mobile App
- Web Admin
- Counter
- Display
- รายงาน PDF
- ใบคิวและเอกสารที่พิมพ์
- Email และข้อความ HTML ที่ระบบควบคุมรูปแบบได้

ลำดับน้ำหนักที่แนะนำ:

| การใช้งาน | น้ำหนัก |
|---|---:|
| ข้อความทั่วไป | 400 |
| ป้ายกำกับ/ปุ่ม | 500 |
| หัวข้อย่อย | 600 |
| หัวข้อหลัก/เลขคิว | 700 |

ควร self-host ไฟล์ฟอนต์ในระบบ Production เพื่อลดการพึ่งพาบริการภายนอก และกำหนด fallback เช่น `Sarabun, "Noto Sans Thai", sans-serif`

### 4.2 วันที่ เวลา และปฏิทินไทย

ทุกหน้าจอที่ผู้ใช้เห็นต้องแสดงปี พ.ศ. และใช้เขตเวลา Asia/Bangkok เช่น:

- วันที่แบบเต็ม: `วันพฤหัสบดีที่ 15 ตุลาคม พ.ศ. 2569`
- วันที่แบบย่อ: `15 ต.ค. 2569`
- วันที่ตัวเลข: `15/10/2569`
- เวลา: `14:30 น.`
- วันที่และเวลา: `15 ต.ค. 2569 เวลา 14:30 น.`

หลักการจัดเก็บและรับส่งข้อมูล:

- Database เก็บ timestamp เป็น UTC หรือชนิดข้อมูลที่รักษา timezone ได้
- API รับส่งเวลาในรูป ISO 8601 เช่น `2026-10-15T07:30:00Z`
- กฎเวลาทำการคำนวณโดยอ้างอิง `Asia/Bangkok`
- แปลงเป็นปฏิทินพุทธศักราชเฉพาะชั้นแสดงผลและรายงาน
- ห้ามบวก 543 ซ้ำกับค่าที่ถูกแปลงเป็น Buddhist calendar แล้ว
- วันที่จากผู้ใช้ต้อง parse ด้วยส่วนกลางชุดเดียว ไม่ให้แต่ละหน้าจอแปลงเอง
- การเรียง ค้นหา และเปรียบเทียบวันที่ใช้ค่ามาตรฐาน ไม่ใช้ข้อความ พ.ศ.
- ปี พ.ศ. เท่ากับปี ค.ศ. + 543 เฉพาะกรณีที่ library ยังไม่ได้แปลงปฏิทินให้

Web สามารถใช้ locale `th-TH-u-ca-buddhist` ส่วน Mobile ต้องกำหนด Thai locale, Buddhist calendar และ Asia/Bangkok อย่างชัดเจน

## 5. บทบาทผู้ใช้งาน

| บทบาท | หน้าที่หลัก |
|---|---|
| ประชาชน | จอง เลื่อน ยกเลิก Check-in และติดตามคิวผ่าน K-QOnline |
| เจ้าหน้าที่เคาน์เตอร์ | เรียกคิว เริ่มบริการ พัก ส่งต่อ และจบงาน |
| หัวหน้าแผนก | เปิด/ปิดช่อง ปรับ Capacity และดูสถานการณ์ของแผนก |
| ผู้ดูแลสาขา | จัดการเวลาทำการ แผนก บริการ และรายงานของสาขา |
| ผู้ดูแลระบบ | จัดการผู้ใช้ สิทธิ์ การเชื่อมต่อ และค่าระบบ |

## 6. K-QOnline Mobile App

ความสามารถหลัก:

1. ลงทะเบียน เข้าสู่ระบบ และยืนยัน OTP หรือวิธีที่องค์กรกำหนด
2. เลือกสาขา แผนก ประเภทบริการ วันที่ และ Slot
3. แสดงเฉพาะ Slot ที่เปิดและยังมี Capacity
4. Hold สิทธิ์ชั่วคราวระหว่างยืนยัน
5. ยืนยันการจองและรับ QR Code/Booking reference
6. ดูคิวข้างหน้าและเวลารอโดยประมาณ
7. เลื่อนหรือยกเลิกตามเงื่อนไข
8. Check-in เมื่อมาถึงสถานที่
9. รับ Push Notification ก่อนถึงเวลาและเมื่อใกล้ถูกเรียก
10. ดูประวัติการรับบริการ

Mobile App ห้ามฝัง database credential, API secret ถาวร หรือข้อมูลส่วนบุคคลลงใน QR Code

## 7. K-QAdmin ระบบหลังบ้าน

### 7.1 Dashboard

- จำนวนคิวตามสถานะ
- Capacity ที่ใช้ไปและคงเหลือ
- เวลารอเฉลี่ยและเวลาให้บริการจริงเฉลี่ย
- จำนวนช่องบริการที่เปิด
- อัตรามาสาย ไม่มา และยกเลิก
- คิวที่เสี่ยงเสร็จหลังเวลาปิด
- Health status ของ API, Database, Redis, Tailscale และบริการแจ้งเตือน
- แสดงระดับความหนาแน่นเป็นเขียว เหลือง และแดง

### 7.2 การเชื่อมต่อ

- สถานะ API และ URL ปัจจุบัน
- สถานะ Tailscale Serve/Funnel
- Database และ Redis health check
- เครื่องออกบัตรคิวและจอแสดงผล
- Push Notification, LINE หรือ SMS provider
- ปุ่มทดสอบการเชื่อมต่อ
- เวลาเชื่อมต่อล่าสุดและข้อความผิดพลาดล่าสุด
- Audit log เมื่อมีการเปลี่ยน configuration

Secret ต้องเข้ารหัสและปิดบังบนหน้าจอ การแสดงหรือเปลี่ยน secret ต้องใช้สิทธิ์ระดับสูงและ MFA

### 7.3 สาขา

- ชื่อ รหัส ที่อยู่ และข้อมูลติดต่อ
- เวลาเปิดและปิดรายวัน
- วันหยุดประจำสัปดาห์
- วันหยุดหรือเวลาเปิดพิเศษ
- ช่วงพัก
- เวลาหยุดรับคิว
- Closing buffer
- สถานะเปิด/ปิดสาขา

### 7.4 แผนก

- รหัสและชื่อแผนก
- สาขาที่สังกัด
- ตารางวันที่และเวลาที่เปิด
- จำนวนช่องบริการ
- ประเภทบริการที่รองรับ
- สัดส่วน Online, Walk-in และ Reserve
- เปิด/ปิดแผนกชั่วคราว

### 7.5 ประเภทบริการ

- ชื่อและรหัสบริการ
- ระยะเวลาเฉลี่ยต่อคิว
- เวลาเตรียมก่อน/หลังบริการ
- ช่องหรือเจ้าหน้าที่ที่ให้บริการได้
- จำนวนสูงสุดต่อ Slot
- ระยะเวลาจองล่วงหน้า
- เงื่อนไขยกเลิกและเลื่อน
- จำนวนครั้งสูงสุดต่อคนต่อวัน
- Priority และเอกสารที่ต้องเตรียม

### 7.6 Override รายวัน

ผู้ดูแลต้องปรับค่ารายวันได้โดยไม่เปลี่ยนค่าแม่แบบ เช่น:

- ปิดสาขาหรือแผนกเป็นกรณีพิเศษ
- ลดหรือเพิ่มจำนวนช่องบริการ
- เปลี่ยนเวลาพัก
- ลด Capacity บาง Slot
- เพิ่มคิวเร่งด่วนหรือสำรอง

Override ทุกครั้งต้องมีเหตุผล ผู้แก้ไข วันเวลา และค่าเดิม/ค่าใหม่ใน Audit log

## 8. K-QCounter และ K-QDisplay

K-QCounter ต้องรองรับ:

- ดูคิว Waiting ตามแผนกและ Priority
- เรียก เรียกซ้ำ ข้าม พัก และย้ายคิว
- เริ่มและจบการให้บริการ
- บันทึก No-show และหมายเหตุ
- เปลี่ยนสถานะช่องบริการ
- แสดงผลกระทบต่อเวลารอทันที

K-QDisplay ต้องรองรับ:

- หมายเลขคิวที่กำลังเรียก
- หมายเลขช่องบริการ
- รายการคิวล่าสุด
- ข้อความประชาสัมพันธ์
- เสียงเรียกคิวภาษาไทย
- รับข้อมูลผ่านช่องทาง realtime แต่ต้องมี polling fallback

## 9. สถานะคิวส่วนกลาง

```text
HELD → CONFIRMED → REGISTRATION_WAITING → REGISTRATION_CALLED
  │         │                  │                    │
  └→ EXPIRED└→ CANCELLED       └→ REGISTRATION_IN_PROGRESS → SENT_TO_DEPARTMENT
```

| สถานะ | ความหมาย |
|---|---|
| HELD | ล็อกสิทธิ์ชั่วคราวระหว่างยืนยัน |
| CONFIRMED | ยืนยันการจองแล้ว |
| REGISTRATION_WAITING | ผู้รับบริการมาถึงและรอห้องบัตร |
| REGISTRATION_CALLED | เจ้าหน้าที่ห้องบัตรเรียกแล้ว |
| REGISTRATION_IN_PROGRESS | กำลังลงทะเบียนและเปิด Visit |
| SENT_TO_DEPARTMENT | เปิด Visit แล้วและส่งผู้ป่วยไปยังแผนก |
| CANCELLED | ถูกยกเลิก |
| EXPIRED | Hold หรือสิทธิ์หมดเวลา |
| NO_SHOW | ไม่มาเมื่อเรียกตามเงื่อนไข |

K-QCENTER เป็นผู้ตรวจสอบและเปลี่ยนสถานะหลักเพียงระบบเดียว Client ส่งคำขอเปลี่ยนสถานะ แต่ห้ามแก้สถานะในฐานข้อมูลเอง

## 10. Slot และ Capacity

Slot คือช่วงเวลาที่ผู้ป่วยต้องลงทะเบียนและให้เจ้าหน้าที่ห้องบัตรเปิด Visit ก่อนส่งต่อไปยังแผนก ไม่ใช่เวลาที่การตรวจรักษาต้องเสร็จสิ้น การจอง Online และการรับบัตร Walk-in ใช้ Capacity รวมของ Slot เดียวกัน การเช็กอินรายการจองที่มีอยู่แล้วต้องไม่หัก Capacity ซ้ำ

### 10.1 ค่าที่ใช้กำหนด

- จำนวนรับรวมต่อวันของแผนก (`departments.daily_capacity`)
- ตัวเลือกไม่จำกัดจำนวนคิว (`departments.unlimited_capacity`) จะข้ามการตรวจ Capacity แต่ยังต้องอยู่ในวันและเวลาที่เปิดบริการ
- ระยะเวลาแบ่ง Slot ของแผนก (`departments.slot_minutes`) หรือไม่แบ่งช่วง
- จำนวนรับที่ผู้ดูแลปรับเฉพาะ Slot
- จำนวนจองรวมจาก Online และ Walk-in
- คิวสะสม
- เวลาพักและเวลาปิด
- Closing buffer

### 10.2 การกำหนดจำนวนรับในระยะนี้

```text
slotEnd = min(slotStart + department.slotMinutes, departmentClose)
slotCapacity = distribute(department.dailyCapacity, numberOfSlots)
```

ตัวอย่าง NCD:

```text
เวลาบริการเริ่ม       07:00 น.
ระยะเวลา Slot         60 นาที
Slot แรก              07:00–08:00 น.
จำนวนรับรวมต่อวัน     ใช้ค่าที่ผู้ดูแลกำหนดในแผนก
```

ระบบยังไม่คำนวณจำนวนรับจากจำนวนแพทย์/ผู้ให้บริการ เวลาเฉลี่ย หรือ Efficiency ค่าเหล่านี้เก็บเป็นข้อมูลประกอบเพื่อรองรับการพัฒนาในอนาคต

### 10.3 การแบ่งโควตาเริ่มต้น

| ประเภท | สัดส่วนแนะนำ |
|---|---:|
| Online | 70% |
| Walk-in | 20% |
| Reserve/Urgent | 10% |

ผู้ดูแลปรับได้ตามแผนกและวัน ระบบอาจคืนโควตาที่ยังไม่ใช้กลับสู่ช่องทางอื่นก่อนเริ่ม Slot ตามเวลาที่กำหนด

ผู้ดูแลกำหนดจำนวนรับรวมต่อวันและระยะเวลาแบ่ง Slot ที่แผนก ระบบกระจายจำนวนรับให้แต่ละ Slot โดยผลรวมไม่เกินจำนวนรับต่อวัน หากไม่กำหนดระยะเวลา ระบบสร้างหนึ่ง Slot ต่อช่วงเวลาทำการ ผู้ดูแลยังปรับจำนวนรับเฉพาะ Slot ได้ และค่าที่ปรับเฉพาะ Slot ต้องไม่ถูกการสร้าง Slot อัตโนมัติเขียนทับ

การแก้ค่ามาตรฐานของแผนกต้องไม่เขียนทับ Slot ของวันปัจจุบันที่สร้างแล้ว และใช้กับการสร้าง Slot ตั้งแต่วันถัดไป การปรับภายในวันทำผ่าน Today Override ได้สองแบบ:

- ปรับจำนวนรับของ Slot รายช่วง โดยห้ามต่ำกว่าจำนวนจองแล้วและห้ามแก้ Slot ที่สิ้นสุดแล้ว
- เพิ่มหรือลดจำนวนรับรวมของช่วงที่เหลือวันนี้ แล้วกระจายเฉพาะ Slot ที่ยังไม่เริ่ม ไม่มีการจอง และไม่ถูกล็อก

Today Override ต้องล็อก Slot ที่แก้ บันทึกค่าเดิม ค่าใหม่ ผู้กระทำ และเวลาใน Audit log และไม่เปลี่ยนค่ามาตรฐานของวันถัดไป

หน้า “Slot และกำลังบริการ” ต้องกรองตามวันที่และจุดบริการ/แผนกได้ โดยแสดงเฉพาะจุดที่อยู่ในขอบเขตสิทธิ์ของผู้ใช้ วันที่แสดงต่อผู้ใช้เป็นพุทธศักราช และอนุญาต Today Override เฉพาะเมื่อเลือกวันที่ปัจจุบัน

### 10.4 ป้องกันเกินเวลาปิด

ระบบอนุญาต Slot หรือการจองใหม่เมื่อ:

```text
predictedFinishTime <= closingTime - closingBuffer
```

เวลาคาดการณ์เสร็จต้องพิจารณางานค้าง ช่องที่เปิดจริง เวลาบริการเฉลี่ยล่าสุด เวลาพัก และคิวพิเศษ หากค่าคำนวณขัดกับเวลาหยุดรับคิว ให้เลือกเงื่อนไขที่ปิดรับเร็วกว่า

เมื่อกำลังให้บริการลดลง ระบบต้อง:

1. ปิดหรือลด Capacity ของ Slot ที่ยังไม่ถูกจอง
2. ไม่ยกเลิกคิวที่ยืนยันแล้วอัตโนมัติ
3. แจ้งเตือนหัวหน้าแผนกเมื่อมีความเสี่ยงล่าช้า
4. เสนอเปิดช่องเพิ่ม ปรับ Slot ถัดไป หรือแจ้งผู้จอง

### 10.5 ป้องกันการจองซ้ำ

- ใช้ database transaction
- ใช้ unique constraint ตามกฎการจอง
- ใช้ atomic counter หรือ lock ที่มีวันหมดอายุ
- Hold มีอายุ เช่น 3–5 นาที
- Booking API รองรับ Idempotency-Key
- การคืน Capacity ต้องเกิดเมื่อยกเลิกหรือหมดอายุอย่างแน่นอน

ข้อกำหนด API:

- ใช้ HTTPS เท่านั้น
- ตรวจ authentication และ authorization ทุก endpoint ที่ไม่ใช่ public จริง
- ตรวจสิทธิ์ระดับ record เช่น สาขาและแผนก
- Validate input และจำกัดขนาด payload
- Rate limit Login, OTP, Slot search, Hold และ Booking
- ไม่ส่ง field ภายในหรือข้อมูลส่วนบุคคลเกินความจำเป็น
- Version API
- มี correlation/request ID
- Error response ไม่เปิดเผย stack trace หรือ secret
- API ที่สร้างรายการต้องรองรับ idempotency ตามความเหมาะสม

## 14. ความปลอดภัย

- MFA สำหรับผู้ดูแลและเจ้าหน้าที่ที่มีสิทธิ์สำคัญ
- Access token อายุสั้นและ refresh-token rotation
- Password hash ด้วย algorithm ที่เหมาะสม ห้ามเข้ารหัสแบบย้อนกลับ
- Secret เก็บใน secret store หรือ environment ที่จำกัดสิทธิ์
- เข้ารหัสข้อมูลระหว่างทางและข้อมูลสำคัญขณะจัดเก็บ
- จำกัด CORS ให้ตรงกับ client ที่อนุญาต
- Rate limiting และตรวจจับ bot/booking abuse
- ป้องกัน Broken Object/Function Level Authorization
- Audit การ Login เปลี่ยนสิทธิ์ แก้ Capacity แทรก/ยกเลิกคิว และดูข้อมูลสำคัญ
- ไม่บันทึก OTP, access token, password หรือข้อมูลส่วนบุคคลเต็มรูปแบบลง log
- Patch ระบบปฏิบัติการ runtime และ dependency สม่ำเสมอ
- สำรองข้อมูลแบบเข้ารหัสและทดสอบกู้คืน
- ทดสอบช่องโหว่ก่อน Production และหลังการเปลี่ยนแปลงสำคัญ
- กำหนด retention และการลบข้อมูลตามนโยบายองค์กรและกฎหมายที่เกี่ยวข้อง

## 15. Logging, Monitoring และ Audit

ต้องติดตามอย่างน้อย:

- API availability, latency และ error rate
- จำนวน Booking/Hold/Expired
- Database/Redis connection
- Queue delay และ predicted finish time
- Login/OTP failure
- Rate-limit events
- การเปลี่ยน config และสิทธิ์
- สถานะ Tailscale และบริการแจ้งเตือน

Audit log ควรมีผู้กระทำ บทบาท เวลา IP/device/context การกระทำ entity ค่าเดิม ค่าใหม่ และเหตุผล โดยผู้ใช้ทั่วไปแก้ไขไม่ได้

## 16. Backup และความต่อเนื่อง

- สำรอง Database ตาม RPO/RTO ที่องค์กรกำหนด
- แยก backup ออกจากเครื่อง Application
- เข้ารหัส backup
- มี restore drill เป็นระยะ
- จัดทำ runbook เมื่อ Internet, Tailscale, API หรือ Database ล่ม

## 18. เกณฑ์ยอมรับเบื้องต้น

1. ทุกหน้าจอและรายงานใช้ Sarabun โดยไม่มีฟอนต์ไทยอื่นแทรกโดยไม่ตั้งใจ
2. วันที่ผู้ใช้เห็นทั้งหมดเป็น พ.ศ. และเวลาเป็น Asia/Bangkok
3. การจองพร้อมกันไม่ทำให้ Capacity ติดลบหรือเกินจำนวนที่กำหนด
4. การกดซ้ำหรือ retry ไม่สร้าง Booking ซ้ำ
5. ระบบไม่เสนอ Slot ที่คาดว่าจะเสร็จหลัง Closing buffer
6. เมื่อปิดช่องบริการ Capacity ในอนาคตถูกคำนวณใหม่
7. K-QOnline, K-QCounter และ K-QDisplay เห็นสถานะเดียวกัน
8. Public client ไม่สามารถเรียก Admin endpoint ได้
9. K-QAdmin ไม่สามารถเข้าจากอินเทอร์เน็ตสาธารณะในรูปแบบทดลอง
10. ไม่มี Database หรือ remote administration port ถูกเปิดผ่าน Funnel
11. ทุกการแก้ Capacity และสถานะสำคัญตรวจสอบย้อนหลังได้
12. Backup สามารถกู้คืนในระบบทดสอบได้

## 21. ลำดับชั้นเวลาทำการ

ระบบแยกเวลาเปิดอาคารออกจากเวลาบริการ โดยใช้ลำดับดังนี้:

```text
อาคาร → สาขา → แผนก → Daily Override
```

- อาคารกำหนดได้ว่าเปิด 24 ชั่วโมง หรือมีเวลาเปิด–ปิด
- สาขาและแผนกมีตารางรายสัปดาห์แยกกัน
- หนึ่งวันมีหลายช่วงเวลาได้ เช่น `08:30–12:00` และ `13:00–16:30`
- วันที่ไม่มีช่วงเวลาถือว่าปิด
- Daily Override ใช้ปิดหรือเปลี่ยนเวลาของสาขา/แผนกเฉพาะวัน
- Override ระดับแผนกปรับจำนวนช่องบริการเฉพาะวันได้
- Slot ถูกสร้างเฉพาะช่วงเวลาที่อาคาร สาขา และแผนกเปิดตรงกัน
- กฎระดับแผนกหรือ Override ที่เข้มงวดกว่าจะมีลำดับเหนือเวลาพื้นฐานของสาขา

## 22. กระบวนการรับคิวและ HOSxP

กระบวนการรับคิวแบ่งเป็น 2 ช่องทาง ได้แก่ การจอง Slot ผ่าน K-QOnline แล้วเช็กอินที่ Kiosk และการรับคิว Walk-in ที่ Kiosk โดยตรง ทั้งสองช่องทางต้องตรวจ Capacity และสร้างคิวผ่าน K-QCENTER API เท่านั้น

รายละเอียดการสแกน QR/กรอกรหัส การอ่านบัตร การสแกน QR ที่ Kiosk หรือจากใบคิวด้วยมือถือเพื่อดู Timeline และเวลารอ การดูสถานะใน K-QOnline การติดตามผ่าน Monitor การเรียกเวชระเบียน การเปิด Visit ใน HOSxP และ SLA ไม่เกิน 120 นาที กำหนดไว้ใน [K-QCENTER-QUEUE-WORKFLOW.md](K-QCENTER-QUEUE-WORKFLOW.md)

## 23. Kiosk Template และเมนูตามจุดบริการ

แต่ละจุด Kiosk ต้องเลือก Template ด้วยรหัสใน URL เช่น `kiosk.html?kiosk=ER` โดย Template ผูกกับอาคารหนึ่งแห่งและกำหนดเมนูหลัก เมนูย่อย แผนก บริการ ลำดับ ตารางเวลาแสดงแยกวันจันทร์–อาทิตย์ และสถานะเปิด–ปิดได้จาก K-QCENTER หลังบ้าน หน้า Kiosk ต้องโหลดการตั้งค่าผ่าน API และต้องไม่เชื่อมฐานข้อมูลโดยตรง

การเปลี่ยน Template จากหน้า Kiosk ต้องยืนยันรหัสผ่านก่อนแสดงรายการ Template อนุญาตเฉพาะบทบาท `admin`, `kiosk_admin` หรือ `kiosk_manager` และต้อง Logout session ที่ใช้ตั้งค่าทันทีหลังเลือกหรือปิดหน้าต่างตั้งค่า

## 24. ผู้ใช้ บทบาท และขอบเขตสิทธิ์

K-QCENTER ต้องจัดการบัญชีจากหน้าหลังบ้านได้ โดยรองรับบทบาท `admin`, `kiosk_admin`, `kiosk_manager`, `counter` และ `viewer` พร้อมขอบเขต `ALL`, `BRANCH` หรือ `DEPARTMENT` การบังคับสิทธิ์และขอบเขตต้องทำที่ API ฝั่งเซิร์ฟเวอร์ ไม่อาศัยเพียงการซ่อนเมนูบน Client

รายละเอียดอยู่ใน [K-QCENTER-USERS-AND-PERMISSIONS.md](K-QCENTER-USERS-AND-PERMISSIONS.md)

รายละเอียดการตั้งค่าและพฤติกรรมอยู่ใน [K-QCENTER-KIOSK-TEMPLATES.md](K-QCENTER-KIOSK-TEMPLATES.md)

## 25. Slot แบบกำหนดเองรายแผนก

- ผู้ดูแลระบบสามารถเปิดโหมด `Slot แบบกำหนดเอง` แยกรายแผนก โดยไม่เปลี่ยนพฤติกรรมของแผนกที่ยังใช้การแบ่งช่วงอัตโนมัติ
- หนึ่งแผนกมีกฎได้หลายกฎ และระบบประเมินจากบนลงล่างโดยใช้กฎแรกที่ตรงกับวัน
- แต่ละกฎเลือกวันจันทร์–อาทิตย์ได้หลายวัน และเลือกสัปดาห์ที่ 1–5 ของเดือนได้หลายค่า หากไม่เลือกสัปดาห์จะหมายถึงทุกสัปดาห์
- แต่ละกฎเพิ่มช่วงเวลาได้หลายช่วง แต่ละช่วงกำหนดเวลาเริ่ม เวลาสิ้นสุด และจำนวนคิวเฉพาะช่วงได้
- ตัวอย่าง: `07:30–08:30 = 40 คิว` และ `09:00–10:00 = 20 คิว`
- ตัวอย่างกฎรายเดือน: วันศุกร์สัปดาห์ที่ 2, 3 และ 4 โดยกำหนดจำนวนรับของแต่ละช่วงให้รวม 100 คิว
- วันที่ถูกปิดในปฏิทินทำการ รวมถึงวันหยุดที่ซิงค์จากตาราง `holiday` ของ HOSxP จะไม่สร้าง Slot แม้ตรงกับกฎ
- ช่วงเวลาต้องไม่ซ้อนกันและต้องอยู่ภายในเวลาที่อาคาร สาขา และแผนกเปิดตรงกัน
- การแก้กฎจะปิด Slot อนาคตที่ยังไม่มีการจองและไม่ได้ล็อก จากนั้นสร้างใหม่เมื่อ API เรียกข้อมูล Slot โดยไม่แก้ไข Slot ที่มีการจองแล้ว
